SVG Studio 架构概览

十二幅透明画布研究，将矢量几何视作可编程媒介

SVG Studio 是一个基于浏览器的矢量可视化实验集。它以 Paper.js 构建精确几何，以 Rough.js 注入手绘质感，在一张 1400×900 的透明画布上输出 12 种风格各异的场景——从植物形态、地铁线路到系统拓扑，全部以参数化方式即时渲染。

Paper.js Rough.js TypeScript Vite Playwright 透明背景 参数化设计

产品定位与核心特性

SVG Studio 不是一个应用或框架，而是一个矢量可视化研究作品集。每个场景都是一个独立的小实验，回答一个具体的设计问题：分层贝塞尔花瓣如何表达径向结构？合成公交系统在交叉处如何保持可读性？系统拓扑如何把服务、队列、存储组织成可观察的整体？

项目的技术核心在于两条管线的融合：Paper.js 负责精确的路径数学（贝塞尔、布尔运算、平滑、等距投影），Rough.js 则为选定元素叠加手绘的粗糙纹理，形成"精确结构 + 有机质感"的视觉张力。

系统架构总览

SVG Studio 是一个典型的前端单页应用 + 自动化测试管线结构。运行时由 Vite 开发服务器将 TypeScript 源码编译后注入浏览器，浏览器端的 Paper.js 在 Canvas 上执行场景渲染。测试侧则由 Playwright 驱动无头 Chrome，逐场景截图并进行像素级质量校验。

图 1 · 系统分层架构

整个系统分为三层，各自职责清晰、边界明确：

浏览器运行时层是渲染的实际发生地。场景函数接收 URL 参数决定渲染哪个场景，调用 Paper.js 的路径、形状、文本 API 在 Canvas 上构建画面；少数场景（如 metro）还会叠加 Rough.js 的手绘外框。渲染完成后，设置 window.__VIS_READY__ 标志位供测试方探测。

构建与开发层负责将 TypeScript 源码、静态 HTML 与场景元数据打包。Vite 提供开发服务器与生产构建，catalog.json 作为场景目录的单一数据源，既被测试脚本读取，也可供外部工具索引。

测试与验证层是项目的质量保障核心。Playwright 启动无头 Chrome，逐场景加载页面、等待就绪标志、截图保存，并通过 pngjs 对输出 PNG 进行像素级分析——验证透明像素比例、可见像素比例和彩色像素数量三道门槛，确保每幅画面都符合设计预期。

设计要点：测试管线的网络拦截策略很有意思——它会拦截所有非本地、非 data: 协议的请求，确保项目在完全离线的环境下仍能正常运行。这既验证了自包含性，也避免了任何意外的外部依赖。

渲染管线与场景机制

12 个场景共享同一套渲染骨架，但每个场景的内部逻辑完全独立。理解渲染管线有助于把握项目的扩展方式。

图 2 · 场景渲染管线

渲染流程是一条简洁的线性管线：

第一步，参数解析。页面加载后，从 URL 的 scene 查询参数中读取场景 ID。未提供时默认渲染 botanical，保证页面不会空白。

第二步，引擎初始化。调用 paper.setup(canvas) 将 Paper.js 绑定到 1400×900 的 Canvas 元素，然后清空项目画布，确保每次渲染都是干净的起点。

第三步，场景分发。一个名为 renderers 的对象字面量作为分发表，将场景 ID 映射到对应的渲染函数。新增场景只需在表中注册即可，无需修改调用方。

第四步，场景执行。每个场景函数内部独立构建自己的几何——贝塞尔花瓣、地铁线路、轨道椭圆、拓扑节点……都使用 Paper.js 提供的 Path、Circle、Rectangle、PointText 等基元。函数内还定义了两个公共辅助：line() 用于绘制带平滑的折线，label() 用于放置统一样式的文本标签。

第五步，视图更新与就绪标记。调用 paper.view.update() 触发渲染，然后将 window.__VIS_READY__ 置为 true。这个标记是测试脚本的同步信号——没有它，测试就不知道什么时候该截图。

此外，画布还监听了 pointermove 和 pointerdown 事件，每次交互都会递增 __INTERACTION_COUNT__ 计数。测试管线会模拟鼠标移动后检查计数是否增长，以验证交互契约确实被触发。

主走查：场景渲染与测试闭环

我们选择"拓扑图渲染测试"作为端到端走查场景。这个场景覆盖了项目最核心的运转路径：从测试脚本启动，到浏览器渲染一幅系统拓扑图，再到截图保存与像素校验——完整走通开发、构建、渲染、验证四个环节。

  1. 启动 Vite 开发服务器
    测试脚本 capture.mjs 以子进程方式启动 Vite，监听 127.0.0.1:4173。它扫描 stdout 中的"Local:"字样来确认服务就绪，超时 15 秒则报错退出。
  2. 无头浏览器加载拓扑场景
    Playwright 启动无头 Chrome，打开 /index.html?scene=topology。网络拦截层确保所有外部请求被阻断，仅放行本地与 data: 协议，验证项目自包含。
  3. Paper.js 绘制系统拓扑
    浏览器端执行 topology() 函数：绘制三个分组框（EDGE / STREAM / PRODUCTS）、八个节点矩形、八条连接线，以及底部的状态指示点。渲染完成后设置 __VIS_READY__。
  4. 截图与交互验证
    测试脚本等待就绪标志，对 #stage 画布以 omitBackground 模式截图保存为 PNG。随后模拟鼠标移动，读取 __INTERACTION_COUNT__ 确认交互事件被触发。
  5. 像素级质量校验
    pngjs 读取 PNG 数据，逐像素统计：透明像素占比 > 8%、可见像素占比 > 3.5%、彩色像素数 > 2500。三项全部达标才算通过，否则抛出错误终止测试。
为什么是这三道门槛？透明像素比例确保画布确实是透明背景而非填充底色；可见像素比例确保画面不是几乎全空；彩色像素数则防止意外的灰度退化或严重褪色。三者结合，形成了一个轻量但有效的视觉回归防线。

测试与质量保障

SVG Studio 的测试策略是视觉回归测试的一个轻量实现。它不做图像对比（screenshot diff），而是做像素级健康度检查——这种设计取舍很符合一个研究型项目的定位：不需要精确到像素的回归，只需要确保每个场景都有实质性的、彩色的、透明背景的输出。

图 3 · 测试校验流程

测试管线的每个环节都有明确的校验点：

加载阶段使用 waitUntil:'networkidle' 确保网络请求完成，再用 waitForFunction 等待 __VIS_READY__ 标志，双重保证场景确实渲染完毕。超时阈值 15 秒。

截图阶段使用 Playwright 内置的 omitBackground 选项，让 PNG 保留透明通道而非填充白色。这是透明背景输出的关键开关。

交互验证阶段先读取交互计数，模拟两次鼠标移动，再读取计数并断言增长。这个机制确保了画布的指针事件监听没有意外失效。

像素分析阶段是质量的最后一道关。它使用 pngjs 读取 PNG 原始像素数据，按 RGBA 四通道逐像素判断：alpha 为 0 计入透明、alpha 大于 20 计入可见、可见像素中 RGB 最大最小之差超过 24 计入彩色。三项指标全部达标才通过。

扩展方式与设计边界

作为一个研究型项目，SVG Studio 的扩展路径非常清晰：

新增场景只需三步——在 src/main.ts 中编写场景函数，在 renderers 映射表中注册 ID，再在 catalog.json 中补充元数据。测试管线会自动遍历所有目录场景，无需修改测试代码。

新增渲染引擎的成本稍高。当前 Paper.js 是主力引擎，Rough.js 作为补充以"叠加绘制"的方式存在（在同一 Canvas 上二次绘制）。若要引入新的矢量库，需要考虑坐标系对齐与 z-order 穿插的问题。

边界说明：这个项目的定位是"可视化研究集"而非"可复用组件库"。场景之间不共享复杂逻辑，也没有抽象出场景基类或插件系统。每个场景都是自包含的函数，这种极简设计使实验成本很低——想试一个新点子，写一个函数就行，不需要理解任何框架约束。
